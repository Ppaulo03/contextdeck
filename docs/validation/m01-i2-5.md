# M01-I2.5 validation — UX, component architecture and performance

Date: 2026-10-10 · Windows 11 · Node 24.14.0 · Electron 44.7.0 · Herdr 0.9.3 (protocol 22).

Scope: no product features. Consistent visuals, reusable components and styles, removal of proven-dead code, a dropdown that works over the ChatGPT view, measured performance work, and a study for M01-I3.

Legend: **Auto** = automated suite · **Harness** = script driving the real Electron app (throwaway profile, disposable Herdr session `m01i2-lab`) · **Pending** = needs the project owner. Harness scripts live outside the repository; numbers below are medians of 3 alternating runs of the same script on a *baseline* clone (commit `1b6c009`) and an *after* clone. The ChatGPT page was logged out in every run (throwaway profile), so ChatGPT-side numbers are lower bounds.

## 2. UI and architecture

See [../design-system.md](../design-system.md). Summary: tokens are the only place for raw values; components are small modules (`dom`, `feedback`, `herdr-store`, `header`, `terminal-view`, `workspace-selector`, `git-panel`, `herdr-panel`) wired in `app.js` with no cycles. The workspace menu is a transparent local overlay `WebContentsView` added on top only while open (trade-offs documented there). The overlay renderer is released 30 s after the menu closes.

Auto: 164 tests (view-model, components against a fake DOM mutation-checked, overlay lifecycle, IPC least privilege, token-driven styles).

Not measured: GPU memory by process kind beyond the totals above; a logged-in ChatGPT profile (personal content, not captured).

### ContextDeck vs ChatGPT cost

~531 MB idle is dominated by Chromium itself: browser 116 MB, GPU 110 MB, utility 55 MB, two renderers ≈ 250 MB (one of them chatgpt.com). ContextDeck's own main process is ~114 MB. ContextDeck's own overhead in CPU and IPC at idle is zero (0 IPC, 0 `setBounds`, 0 pushes over 25 s); the remaining cost belongs to the ChatGPT page and Chromium. No Chromium switch was changed: none would help without weakening isolation, and the measured costs are not in ContextDeck's control.

### Chat view lifecycle

One `WebContentsView`, created once and kept; tab switch only attaches/detaches it; 0 reloads during switching in all runs. Listeners are registered once (pinned by a structural test).

## 5. M01-I3 preparation: single view vs one view per conversation

Measured with plain Electron on a throwaway partition (logged-out `chatgpt.com`, N = 1…6 views):

| Views loaded | Total memory | Per additional view | Process count |
|---|---|---|---|
| 1 | 457 MB | – | 5 |
| 3 | 728 MB | ≈ 135 MB | 7 |
| 6 | 1133 MB | ≈ 135 MB | 10 |

- Each view gets its own renderer process (≈ 130–140 MB), even sharing the partition (session, cookies shared).
- Switching between already loaded views (detach/attach): median 5 ms, max 7.5 ms, 0 reloads. Idle CPU with 6 loaded views: 0.25 %.
- Closing 3 of 6 freed ≈ 420 MB; recreating one cost 285 ms to load logged out.
- A *single reused view* navigating between conversations: median 178 ms per navigation (full app shell load), and any answer streaming in the conversation left behind is abandoned.

| Strategy | Memory | Switch time | In-progress conversation | Verdict |
|---|---|---|---|---|
| Single reused view | lowest | ~180 ms+ (lower bound) | lost on navigate | Simple, but loses work |
| One view per conversation, all kept | ~135 MB × N | ~5 ms | preserved | Fast, unbounded memory |
| **Lazy creation + bounded pool (recommended)** | ~135 MB × pool size | 5 ms for pooled, ~300 ms+ otherwise | preserved for pooled | Best trade-off |

**Recommendation for M01-I3 (not implemented):** create a view the first time a workspace's conversation is opened (lazy), keep a small LRU pool (suggest 3–4 views ≈ 400–550 MB), and never destroy a view that is streaming or has unsent input; the evicted conversation reloads by URL on next use. All views share the existing persistent partition (one login). Numbers must be re-measured logged in before fixing the pool size, since real conversation pages are heavier.
