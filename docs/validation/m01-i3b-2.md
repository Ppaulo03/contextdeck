## A. Integration diagnosis (before changing anything)

| # | Topic | Finding | Consequence |
|---|---|---|---|
| 1 | I3P detector/observer | `createStateObserver(contents)`: probe in an isolated world (booleans only), model with epoch/identity guards, `visible`/`viewed` inputs, poll chain 1 s responding / 2 s visible idle / 5 s hidden idle; wired only to the original M00 page behind `CONTEXTDECK_CHAT_OBSERVER=1`, diagnostics log | Reuse it as is for every view; a second detector would diverge from the evidence gathered in I3P |
| 2 | Chain fragility | A probe whose renderer never answers never settles → the poll chain ends silently | Add a probe timeout (5 s) |
| 3 | Concurrency of many observers | Every observer would first poll at the same instant after creation | Stagger the first poll (`phaseMs`) |
| 4 | `ChatViewManager` | Owns views, identity (`c:<uuid>`) and lifecycle events; `list()`, `get()`, `onChange`, `handleOf()` (the handle exposes `contents`) | The hub follows `manager.onChange`; no view is created or touched to observe |
| 5 | `ChatNavigator` | Builds the strip state; tab ⇄ view is by identity; explicit actions (select, new, temporary) | Activity is read per view with an identity check; explicit actions are *visits* |
| 6 | Runtime contract | `AttentionState` was `pending | acknowledged`; `fromObserverState` stamped readings with "now" | Spec: `none | pending`; readings must carry the probe's own time so they expire |
| 7 | Model identity | The model compared identity by *key* (`g:<project>/c:<id>` vs `c:<id>`), so a Project route reset what it had learned | Compare by conversation id |
| 8 | Visibility semantics | I3P `visible` was "chat tab showing"; `viewed` came from the tab switch | `user-visible` = attached view + chat tab + window shown, not minimized and focused; visits are explicit |
| 9 | M00 page | Created at startup, unscoped, never navigated (I3B-1) | Observed like any other view (it was the only one before) |
| 10 | Layout/design | Strip has a fixed 34 px height; tabs are pills; tokens only | Fixed-size status slot per tab; no new bar; selector trigger/menu get small badges |

### States and evidence

| Dimension | Values | Evidence |
|---|---|---|
| PageLifecycle | loading, ready, error, destroyed | navigation events (observed) |
| GenerationState | unknown, idle, **responding**, **ended-unclassified**, completed, interrupted, error | `responding`: the stop control (observed). `ended-unclassified`: the stop control stopped being observed with the composer back. `completed`: only with a finished-turn action (inferred), `interrupted`/`error`: only with their own notice (inferred). Never derived from `ended-unclassified` |
| DraftState | unknown, empty, present | probe boolean (observed); text never read |
| AttentionState | none, pending | policy below |

### Attention policy

`pending` when an observed `responding` stops being observed **while the view is not user-visible**. It is not set by a lost probe, a reload, an identity change, a destroyed view or an expired reading. Cleared only by a visit while the view is user-visible: tab click / new conversation / selecting it; the chat tab or the window becoming interactive with it on screen; typing into it. Not cleared by selecting the workspace, an automatic restore (Auto mode, startup), creating or pre-loading a view, a state push, or by it being "selected in the data". **A visit is not proof that the user read anything** and the indicator says "Atividade para revisar", not "concluída".

### Identity and background

A → B inside a view: the model resets (epoch), A's tab shows nothing about that page, B's tab shows B only once observed, a late probe answer is dropped by epoch; a new chat that gets its address while responding keeps its state and is not bound; Project and plain routes are one identity; a redirect leaves the placeholder tab without status. Hidden (detached) views keep being observed through `executeJavaScriptInIsolatedWorld` (independent of the page's timers and `requestAnimationFrame`); nothing re-attaches a view; the worst-case latency is the poll interval (hidden idle 5 s).

### Failure behaviour

Page loading → no status. Composer missing / DOM changed / probe error / lost answer / expired reading → `unknown` (shown as `?` only for a loaded, probed view) and **no attention**. Renderer busy → probe times out after 5 s and polling resumes. View destroyed → observer, listeners and timers go with it. Observer cannot start or throws → that view has no status; views, bindings, Herdr and navigation are untouched (tested, including a 120 s probe-error storm and a harness page frozen for 7.5 s).

## C. Interface

Tab = text + a fixed-size status slot (always present, never changes the tab's width): ring spinner (responding), `●` (activity to review), `✎` (unsent draft), dashed `?` (unknown). Each combination is announced in the tab's accessible name ("A1, Respondendo, Rascunho não enviado") and in its tooltip; shapes differ so nothing depends on color alone; the spinner is the existing keyframes (disabled by `prefers-reduced-motion`); tabs stay clickable and keyboard-focusable and keep focus across updates. The workspace selector shows `↻n ●m` for the **other** workspaces, and each row of the workspace menu shows its own; a workspace with no loaded conversation shows nothing (it is not "idle"). The header is unchanged.

## E. Risks and limitations

1. **Polling.** A response shorter than the poll interval can start and end between two observations: no indicator, by design (no speculative detection). A hidden view's *start* of a response is noticed within 5 s.
2. **`ended-unclassified`.** The end of the stop signal is all that is known; "● Atividade para revisar" does not tell whether the answer completed, was stopped or failed. `completed` appears only if the finished-turn action signal is ever found; the UI deliberately does not distinguish.
3. **Selector dependence.** The detector's selectors/labels are the I3P findings: a ChatGPT UI change makes views degrade to `?` (safe), never to false activity.
4. **First observation delay.** After a load the first poll is staggered up to ≈ 4.3 s; nothing is claimed before it.
5. **Window focus semantics.** "User-visible" requires the window to be focused: a response ending while another app has focus, even with the conversation on screen, is pending until you come back (a visit on focus clears it).
6. **Keyboard visit.** Typing into the visible page counts as a visit; there is no mouse-based visit signal (Electron exposes none for the page) other than tab clicks and window focus.
7. **Per-view cost.** One observer per loaded view (a timer and a ≈ 1 ms probe every 2–5 s); memory per view is unchanged (≈ 135–160 MB, dominated by the renderer).
8. **Initial page.** The M00 page is observed like any view; the I3P diagnostics log now covers every view (tagged) when `CONTEXTDECK_CHAT_OBSERVER=1`.
9. Counts are derived and not persisted: after a restart nothing is "pending" (a response cannot survive the application anyway).

## F. Manual homologation (Windows, ChatGPT logged in, real Herdr)

Preparation: back up `ui-state.json` and `chat-bindings.json`; workspaces A and B with bound conversations (A1, A2, B1…); `npm start`. Do not automate prompts; send your own. `CONTEXTDECK_CHAT_STATUS=0` turns the feature off if you need to compare.

**A — Response in the background**
1. Open A1; send a long request yourself. A1's tab shows the spinner.
2. Switch to A2, then to workspace B. A1 keeps responding (it is the same page, no reload). The selector shows `↻1` for the other workspace.
3. Wait for the answer to end. A1's tab shows `●`; the selector/menu shows `●1` for workspace A.
4. Return to workspace A: the `●` is **still there** (automatic restore is not a visit). Click A1: it clears.
5. Repeat but stay on A1 while it finishes: no `●` appears (you were looking at it).

**B — Two responses**
1. Start answers in A1 and A2. Go to workspace B. A shows `↻2`; each tab has its own spinner. Check nothing reloaded (scroll, composer text).

**C — Draft**
1. Type (do not send) in A1. Switch workspace: A1's tab shows `✎` within ~5 s. Return: the text is intact. Clear the text: the `✎` disappears.

**D — Navigation inside ChatGPT**
1. In A1's page click another conversation in ChatGPT's own sidebar (one that is bound to A and one that is not). The tab of what is on screen is the active one; the old tab shows nothing from this page; an unbound conversation appears as a chip. Start an answer there: the indicator follows the conversation on screen, not the old tab.

**E — Uncertainty**
1. Press Stop during an answer (hidden): you may see `●` (activity to review) or nothing — never a claim that it completed. 2. Reload a page (Recarregar) while it answers: no `●` appears because of the reload. 3. Everything stays clickable and the strip stays usable.

**F — Regression and performance**
1. Switch quickly between workspaces and chats; the app stays responsive and no tab changes width when indicators appear or disappear. 2. Login/clipboard/upload still work. 3. Minimize the window while an answer is running in the visible conversation, wait for it to end, restore: `●` is there and clears when the window gets focus with that conversation on screen. 4. Watch memory with 4–5 loaded conversations (Task Manager): ≈ 135–160 MB per conversation, no growth from observing.
