# M01-I3C-1 — view lifecycle foundations and safe suspension: validation record

Status: **implemented, awaiting manual homologation; lifecycle safety rules were tightened in [I3C-1H](m01-i3c-1h.md).** This record captures the original I3C-1 implementation and its measurements. Decision: [0005](../decisions/0005-view-lifecycle.md). Base: M01-I3B-3 (`ee514b0`, homologated 9/9). Branch `feature/m01-i3c-1-lifecycle-foundations`. Automatic suspension (LRU, timers, thresholds) is **not** implemented.

Four categories, kept apart:

- **Validated automatically** (node `--test`, structure pins).
- **Validated by harness** (real Electron, throwaway profile, logged-out chatgpt.com, fake Herdr; `test/electron/lifecycle-harness.js`).
- **Pending manual validation** (a person, real profile and a logged-in account).
- **Blocked / not measured** (stated explicitly below).

## 1. Audit of the lifecycle (what existed)

| Subject | Finding |
| --- | --- |
| Creation | `ChatViewManager.create()` only, on demand (selecting a tab, "Nova conversa", opening a page of the exceptional list, the initial `pristine` page). Every view is its own `WebContentsView` on the one persistent partition. |
| Destruction | Only `destroyAll()` at window close. No eviction. Hidden views are detached (`removeChildView`), not destroyed, and keep running. |
| Residual pages | Created by `releaseConversation` (unbind), `releasePage` / `focusExisting` / `backFromConflict` / `transfer` (the other page of a transferred conversation), and the Project-creation failures. All become `scope: null` pages ("exceptional list"); none is ever reclaimed before shutdown. |
| Deduplication | `duplicates()` reports two views on one conversation; neither is destroyed. |
| Listeners / timers | Per page: the `chat-view.js` listeners (die with the WebContents), one `StateObserver` (its own poll timer + 7 `contents` listeners, removed on `stop()`). Global: one sweep timer in the hub. Verified here: after a release no listener of the old contents remains and no timer is left (test `suspending releases the page…`). |
| Bookkeeping maps | `navigator`: `contextual`, `busyMemo`, `choice` were keyed by view id and never pruned (views never disappeared). They are now pruned on every `reconcile()`. `context-adoption` maps are keyed by view id too, but only pages with a note / pending creation have entries, and those are not suspendable. |
| Observation | Hub entry per view; events of an observer that was stopped find no entry. A stale `loaded` of an older load is already ignored by `loadSeq`; events of a removed view id are dropped by the manager. |
| Overlays | Independent of views (one overlay view). A decision modal blocks nothing about views; a page with a pending decision is simply not eligible. |

Conceptual states, mapped onto the existing structures (nothing new is stored): `created` (page `loading`, first load) → `active` (selected) / `background` (alive, not selected) → `suspended` (a record in the manager, no page) → `restoring` (page `loading` after a suspension) → `active`. `lifecycle.inventory()` derives them on demand.

## 2. Inventory and architecture

```text
navigator.lifecycleFacts(viewId)  (kind, scope, selected, binding, conflict, duplicate, creating, decision, switching, summary, recoveryUrl)
              │
              ▼
lifecycle.blockers(facts, {notBefore})  ── pure ──► reasons[]  (empty = eligible)
lifecycle.describe / inventory / summary / byBinding   (reads; no polling)
lifecycle.suspend({viewId}) : judge → hub.probeNow(viewId) → judge again (sync) → manager.suspend(viewId, {url}) → emit → hub stops observer → page destroyed
              │ chats:suspend  (UI window and overlay; arguments only name the target)
manager.suspended: key → { id, key, url, at }   (memory only; consumed by create())
```

`kind`: `binding` (the tab of a conversation bound to its own workspace), `residual` (unscoped, not the initial page), `temporary` (a page under a workspace without a binding of its own), `pristine` (the initial page). Files: [chat-views/lifecycle.js](../../src/main/chat-views/lifecycle.js), [chat-views/resource-report.js](../../src/main/chat-views/resource-report.js), [shared/lifecycle-view.js](../../src/shared/lifecycle-view.js) (words), plus changes in `manager.js`, `navigator.js`, `observation.js` (`probeNow`), `ipc/chats.js`, `window.js`.

## 3. Eligibility (every row must be false for a page to be suspendable)

| Reason code | Blocks when |
| --- | --- |
| `selected` | it is the selected view (also while the Terminal tab is showing: it is what comes back on screen) |
| `initial-page`, `temporary-page`, `no-recoverable-identity` | the app's initial page; a page under a workspace without binding; a page without a durable address |
| `not-ready`, `navigating` | loading (first load, restoring, any navigation), error, destroyed |
| `identity-unconfirmed`, `recovery-url` | shows another conversation than it stands for, never showed it (redirected away), observer disagrees; the recovery address does not parse to the same conversation |
| `creating`, `pending-decision`, `conflict`, `duplicate`, `workspace-switching`, `binding-unavailable` | a creation started here has no id yet; a question / failed association is pending; bound to another workspace; another page shows it; a workspace switch is in progress (also if it starts while the fresh reading is awaited); orphan / other-session binding |
| `observation-unavailable`, `observation-stale`, `state-unknown` | not observed, not ready, no reading, reading older than this request, generation unknown / unsupported by evidence (a probe error or timeout lands here) |
| `uncertain`, `responding` | response believed in progress on thin evidence; responding |
| `draft`, `draft-unknown` | an unsent draft; draft state not readable (unknown is **not** empty) |
| `attention` | activity ended unseen and not yet visited |
| `operation-in-progress` | another suspension of this page is under way |

`ended-unclassified` is accepted only when all of the above are clear (it carries no evidence). `completed` / `interrupted` / `error` likewise. Never offered: a button for an ineligible page; it shows the reasons instead (Gerenciar row, tooltip on the strip tab).

## 4. What the user sees

- **Gerenciar** (per binding): a line with the state ("Em segundo plano", "Suspensa (não monitorada)", or the reasons it cannot be suspended) and, only when eligible, **Suspender conversa**. The result message says what happened (or the reasons).
- **Conversation strip:** a suspended tab is italic with a distinct glyph (⏸, label "Suspensa") and a tooltip; an observed idle tab says "Ociosa (observada)" in its tooltip; blocked tabs explain why. Selecting a suspended tab restores it (spinner while loading).
- **Exceptional list** (activity center): suspended pages say "Suspensa (não monitorada)"; **Suspender** appears only for eligible residual pages; *Abrir* restores.
- Totals: `suspended` is reported apart from `loaded`/`observed`. No notice, sound or attention is produced by any lifecycle action.

## 5. Measurement

### Method and limits (read before the numbers)

- Tool: `app.getAppMetrics()` (working set per process, KB → MB) joined with the OS process id of each view (`resource-report.js`), sampled after settling; CPU is the use since the previous call, so each sample calls it, waits (1.5–12 s) and reads again. `npx electron test/electron/lifecycle-harness.js` (HARNESS_OUT for the report). Three consecutive runs are preserved in [harness-reports/](harness-reports/) (`m01-i3c-1-harness-run{1,2,3}.json`, Electron 44.7.0 / Chromium 152, Windows 11).
- **No memory is attributed to a single view.** In every run each view had its own renderer process (`sharedHosts: 0`), but Chromium may share one; the report marks shared processes and never splits them. `viewHostsMB` (sum over the distinct processes that host a view) is an upper bound of what the views cost, not their cost; GPU, Browser and Utility processes are shared by everything.
- Working set counts shared pages in every process that maps them: **use deltas, not totals**. Absolute totals drift between runs (±100 MB) and Chromium trims background renderers by itself (the "before suspending" sample was 237 MB lower than the "10 views" sample in run 1, 21 MB and 32 MB in runs 2 and 3), so a "before" taken right after creating views is not comparable with one taken minutes later.
- **Logged-out profile, a fake composer in the page.** Real logged-in conversations are heavier (long histories, scripts), so the figures are a lower bound; the restore time is the time of a logged-out page. Nothing was measured on the real account (blocked: no logged-in ChatGPT in the agent session).
- Switch time is the main-process time of `selectBinding()` (the compositor painting a page is not included).
- Chromium may keep memory allocated after a page is destroyed; the samples after releasing were taken at +0 s, +3 s and +10 s.

### Results (three runs; Electron 44.7.0, Windows 11)

| Scenario (ChatGPT tab unless said) | Processes | All processes (MB) | View hosts (MB) | Idle CPU, all processes |
| --- | --- | --- | --- | --- |
| Terminal active, only the initial page | 5 | 465–482 | 130–133 (1 view) | 1.0–1.8 % |
| ChatGPT active, 1 conversation (2 pages) | 6 | 604–656 | 265–286 | 0.1 % |
| 3 conversations (4 pages) | 8 | 880–973 | 536–595 | 0.1–0.2 % |
| 5 conversations (6 pages) | 10 | 1150–1249 | 802–870 | 0.1–0.35 % |
| 10 conversations (11 pages) | 15 | 1833–1944 | 1476–1559 | 0.1–0.3 % |
| Terminal active with those 10 conversations | 15 | 1821–1930 | 1465–1547 | 0.26–0.32 % |
| After suspending 5 of the 10 (+10 s) | 10 | 1001–1190 | 649–811 | 0.06–0.22 % |
| At rest with suspended conversations (12 s) | 10 | 999–1190 | 648–812 | 0.05–0.07 % |

- Roughly **135 MB and one process per conversation view**, hidden or not. Having the Terminal tab active changes nothing (−10 MB, noise): hidden views keep their memory. Residual pages are ordinary views (same cost); a separate residual sample was not taken.
- **Suspension (5 of 10):** view hosts 1245 → 649 MB (run 1), 1453 → 781 (run 2), 1527 → 811 (run 3): **−596 / −672 / −716 MB (−48 % / −46 % / −47 %)**, whole application −600 / −678 / −722 MB; processes 15 → 10. Memory was already down at +0 s and fell only 10–15 MB more by +10 s. This is an observation about a logged-out profile, not a promise for real conversations.
- **Time to release:** the synchronous part (`manager.suspend`) 0.3–2.6 ms (the first release of a run: 76 ms once, 1.4–2 ms otherwise); the judgement including the fresh probe 1.2–3.4 ms; until the page is actually destroyed 14–23 ms (first of a run up to 99 ms). `contents.close()` is asynchronous: a page can still be listed for a few ms after the release.
- **Time to restore (create → page ready):** 245 / 304 / 298 ms by the manager, 266 / 332 / 314 ms measured around `selectBinding` + load (logged-out page, includes network). Creating a view for the first time: median 309–323 ms.
- **Switching** between loaded views: median 3.9–5.8 ms, max 18 ms (main process).
- **Idle CPU:** all within 0.05–0.5 % of one core in every state; suspending did **not** produce a CPU difference larger than the noise, and none is claimed.
- **Impact on observers:** one observer per live page (11 → 6 after releasing 5; hub `observers` follows `chatPages`); the 12 s at-rest window polled 19 times for 6 observers (hidden-idle interval), not for suspended pages.
- **New IPC at rest:** 0 `chatnav:state` and 0 `chats:state` pushes in the 12 s window with suspended conversations, in all three runs.

### Harness checks (29 per run, all three runs passed, exit 0)

Inventory and counts; initial page and selected view never eligible; a response in progress and an unsent draft refuse the suspension (page still alive); activity ended unseen (attention) refuses it and the refusal does not clear it; 5 idle background conversations become eligible and are suspended; their pages are destroyed; 11 → 6 pages with observers following; suspended tabs stay in the strip, marked, with no status; bindings file byte-identical; nothing pushed to the UI at rest; suspended pages not polled; restoring creates exactly one page (repeated requests included), shows loading, comes back with relation `match`, one view for the conversation and an observer; no Herdr command in any step; an unbound conversation's page appears as residual, is suspended, stays listed and is restored from the list; a conversation of another workspace is suspended and restored in its workspace; switching workspace restores nothing by itself; closing the window closes every page.

New: `test/view-lifecycle.test.js` (inventory, every eligibility rule positive and negative, the fresh reading catching a draft / response that appeared after the last poll, simultaneous requests, selection during the suspension, workspace switch during it, shutdown during it, late events of a released page, restoration (same session, stored address, one view, no Herdr command, no binding change), Herdr offline, recreated (suspect) workspace, project addresses, another workspace, residual pages (suspend, restore, no identity, becomes a tab if bound), no timers / pushes at rest, repeated cycles leave no listeners / observers / records, IPC validation and trust, view-models, resource report). ## 7. Not run / not measurable here

- A logged-in account, real conversations, a real Herdr session, real keyboard / Explorer paste / ChatGPT-ZIP paste: **not run** (cannot be exercised without a person).
- A crash of the app, or Herdr reconnecting while a restoration is loading, with a live Herdr: covered by unit tests with mocks only (closing during a suspension and a Herdr disconnect / reconnect during a restoration are tested); the harness does not drive a live Herdr.
- Stale ChatGPT sessions (expired login) on restoration: not simulated; a restored page would simply show the login page and, as for any page, nothing is bound.

## 8. Known limitations (the first two are also stated in the help text of the button)

1. Restoring is a reload: scroll position, expanded UI, an attachment not yet sent and any transient page state are lost; the conversation needs the network and a valid login.
2. Only bound conversations and residual pages with a durable address can be suspended. A temporary page of a workspace cannot (there is no safe way back to it).
3. A page the detector cannot read is never suspendable (that is intentional: unknown blocks).
4. A suspended conversation is not observed: it can raise no "activity to review" until it is restored.
5. Chromium may not return all memory; savings differ by page.
6. A closing page is destroyed asynchronously (a few ms).

## 9. Manual checklist (pending a person, real profile, logged in; do not screenshot the ChatGPT view)

Back up `ui-state.json` first. Optionally run with `CONTEXTDECK_LIFECYCLE_LOG=1` (appends to `%APPDATA%\Project Dock M00\diagnostics\lifecycle.jsonl`; open it and send me the lines, they hold no conversation content).

- **A. Suspend an idle conversation.** Open conversations 1–3 of a workspace, select #3. In *Gerenciar*, #1 should say "Em segundo plano" with **Suspender conversa**. Click it: the strip marks #1 "Suspensa". Task Manager / `getAppMetrics`: one fewer renderer.
- **B. Restore it.** Click the suspended tab: spinner, then the same conversation. Check scroll position (expected: lost), that no second tab appeared and that Herdr did not change workspace.
- **C. Responding.** Start a long answer in #2, select #3. *Gerenciar* must show #2 with "Está respondendo." and no button; the IPC (if forced) refuses.
- **D. Draft.** Type (do not send) in #2's composer, select another. #2 must say "Há um rascunho não enviado." and no button. Clear the text, wait ~10 s, the button appears.
- **E. Uncertain / unreadable.** Put a conversation in a state the app flags with "?" (or one that has just ended unseen: "Atividade para revisar"). No button; the reason is shown. After visiting it, the button may appear.
- **F. Residual.** Unbind a conversation whose page is open (Gerenciar → Desvincular). It appears under "Fora de um workspace" in the activity center; if idle, **Suspender** is offered; suspend, then **Abrir** restores it (in the selected workspace's context, under the usual rules).
- **G. Another workspace.** Suspend a conversation of workspace A; switch to B and back to A: it must still be suspended (nothing restores by itself); selecting it restores it.
- **H. Observability.** After B, the restored conversation is observed again (type a draft: the pencil appears). While suspended it never shows as idle and raises no notice.
- **I. Memory with several conversations.** Open 5–10 conversations; note Task Manager totals (or the log), suspend 3–5 idle ones, wait 10 s, note again; restore one and time it. Compare with the logged-out figures above.
- **J. Regressions.** Herdr: select workspaces, terminal works; Projects (if `CONTEXTDECK_PROJECTS=1`): "Nova conversa" and conflicts as in I3B-3; multi-chat switching; clipboard / Git copy and ZIP paste as in M00. Close the app with suspended conversations: it exits cleanly; reopen: nothing is suspended, nothing is lost, bindings intact.
