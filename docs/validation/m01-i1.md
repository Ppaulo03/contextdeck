# M01-I1 validation — Herdr workspace discovery

Date: 2026-10-10 · Windows 11 Pro 10.0.26200 · Node 24.14.0 · Electron 44.7.0 · **Herdr 0.9.3** (stable channel, API protocol 22, schema_version 1).

Scope: read-only discovery of the workspaces of the Herdr session ContextDeck uses, change tracking, and the investigation of whether ContextDeck can know which workspace is visible in **its own** Herdr client. Nothing in M01-I1 creates, selects, renames or closes workspaces from the app; no ChatGPT behaviour depends on Herdr yet.

Legend: **Auto** = automated suite · **Harness** = script driving the real Electron app and a real Herdr server on Windows · **Pending** = needs the project owner.

## 1. Result

**Per-client focus identification: NÃO.** Herdr's public API exposes one session-wide focus (the last focus change made by *any* client or API call). It carries no client identifier, so ContextDeck cannot know which workspace its own client is showing when more than one workspace exists. The integration reports this honestly (`ambiguous`) instead of guessing. Evidence in section 5.

What *is* reliable and implemented: the list of workspaces with stable ids and names, their directories, change/rename/removal detection, recovery after disconnects and server restarts, and a forced `known` answer when the session has exactly one workspace.

## 2. API contract found (verified, not assumed)

Sources: `herdr api schema` (102 request methods, subscription/event schemas), `herdr --skill`, `herdr session list --json`, and live exchanges.

- **Transport (Windows):** a **named pipe** `\\.\pipe\<socket_path>`, where `socket_path` is what `herdr session list --json` reports per session (e.g. `C:\Users\<user>\AppData\Roaming\herdr\sessions\<name>\herdr.sock`). The `herdr.sock` file on disk is only a 24-byte descriptor (`<server pid>:<id>`), **not** a connectable socket; `net.connect(<that path>)` is not the transport. A second endpoint `herdr-client.sock` serves the private client protocol and is not used.
- **Framing:** one JSON document per `\n`. Request `{"id", "method", "params"}`; success `{"id", "result": {"type": …}}`; failure `{"id", "error": {"code", "message"}}`.
- **Read methods used:** `ping`, `session.snapshot`, `workspace.list`, `workspace.get`. `events.subscribe` streams over the same connection after `{"result": {"type": "subscription_started"}}`.
- **Identifiers:** workspace `w<n>`, tab `w<n>:t<m>`, pane `w<n>:p<k>`. Opaque, stable handles; **never reused** (probe: closed `w4`, next workspace was `w5`; an earlier closed `w2` did not return) and **stable across a server restart** (ids, labels and the focus were restored after `herdr session stop` + restart of a lab session).
- **Events (workspace/tab/pane):** `workspace_created|updated|metadata_updated|renamed|moved|reordered|closed|focused`, `tab_*`, `pane_*`, delivered as `{"event", "data"}`. **No sequence number and no client id** in any of them.
- **Per-client concepts in the public schema:** only `client.window_title.set|clear` (error reason `no_foreground_client`, i.e. the server tracks one "foreground client") and `client_shell.surface.set {active}`. There is no method or field that lists clients or reports a client's current workspace.

### Documentation vs installed implementation

- The official agent skill (`herdr --skill`) tells agents not to inspect the session from outside Herdr; that is guidance for agents running *inside* panes. The API itself is reachable from outside, and the skill recommends named test sessions for experiments, which is what was done.
- No document describes the wire transport; it was determined empirically (section 4) and cross-checked with `herdr session list --json`.
- Skill text: "Closed tab and pane IDs are not reused" (workspaces unspecified): measured, workspace ids are not reused either.
- `herdr status` shows version, protocol and capabilities but **no client list**.
- `workspace.focus` is documented as a focus command; its effect on *other* clients is not documented (measured in D below: it moves all of them).
- `herdr api schema` accepts `--json` or `--output PATH`, not both; redirecting its output with Windows PowerShell 5.1 adds a BOM.

## 3. Strategies considered

| Option | Verdict |
|---|---|
| Events as the source of state | Rejected: no sequence number; duplicated/lost/reordered events cannot be detected. |
| Polling `session.snapshot` | Wasteful and still late. |
| **Events as signals + authoritative snapshot (chosen)** | Subscribe first, read the snapshot, re-read on a coalesced signal, plus a 60 s heartbeat and a re-read after each reconnect. Duplicates, delays and gaps are harmless because state always comes from the latest snapshot. |
| Parsing the TUI screen or inferring from "last event after my keypress" | Not implemented, by requirement. |
| Spawning `herdr workspace list` per read | Works, but costs a process per read and gives no push. Only `herdr session list --json` is spawned (to locate the endpoint). |

## 4. Experiments

All mutation happened in **disposable sessions** named `m01i1-lab*` (removed afterwards with `herdr session stop/delete`); the user's `default` session and the app's own `project-dock-m00` session were only read. Clients were real Herdr clients in ConPTY; what each one displays was read back by reconstructing its screen with `@xterm/headless` and looking for a unique marker echoed into each workspace's pane (verified through `pane.read`).

**A — single client.** Client A moved with `next/previous_workspace` keys and with the API: after every step A's screen showed exactly `focused_workspace_id`, and `workspace_focused`/`tab_focused`/`pane_focused` events fired.

**B — two clients on one session.**

| Step | Client A shows | Client B shows | API `focused_workspace_id` |
|---|---|---|---|
| B1: key in B only | `w1` | `w2` | `w2` |
| B2: key in B only | `w1` | `w3` | `w3` |
| B3: key in A only | `w3` | `w3` | `w3` |
| B5: key in A only | `w1` | `w3` | `w1` |

The API follows whichever client moved last. Final row: A is on `w1`, B is on `w3`, the API says `w1`: the visible workspace of B (or of A, if B moved last) cannot be derived from anything the API returns. Events for these moves are identical in shape for both clients. Attaching a second client produced no focus event.

**C — recovery.** Killing a client leaves the session running; a new client attaches on the session's last focus (not on where the killed client was). Breaking and re-creating the event subscription and re-reading the snapshot restored the state.

**D — API focus with divergent clients.** With A on `w1` and B on `w2`, `workspace.focus w3` moved **both** to `w3`; keys in one client afterwards moved only that client. So an API focus command is global (and would move the user's other clients), while TUI navigation is per client.

**E — server restart (lab server only).** `herdr session stop`: the event stream closed, API calls failed with `ENOENT`; restarting the server restored ids `w1,w2,w3`, labels and focus, and the observer reconnected on its own.

## 5. Classification and evidence

**NÃO** — the protocol does not give enough information. Reasons: no client identifier anywhere; session focus is last-writer-wins (B1–B5); API focus is global (D); client enumeration is absent; the only per-client notions are `foreground client` (single, write-only) and a private protocol that is out of scope. A *sole-client* condition would make `focused_workspace_id` correct (scenario A) but cannot be verified, so it is not used. The single case with certainty is a session with exactly one workspace.

Internal model (`workspace-reader.js`): `identifyActiveWorkspace` returns `known` (only one workspace, evidence `only_workspace`), `ambiguous` (several; the session focus is exposed only as `candidateId`, evidence `session_focus_last_writer`) or `unknown` (no data / no workspaces).

## 6. Architecture decisions

- Windows named-pipe client restricted by an **allowlist of read methods** and of subscription types; mutating or unknown methods are rejected before any connection is opened (tested).
- Endpoint located with the official `herdr session list --json`, with `HERDR_*` stripped from the child environment (same isolation as the PTY).
- One `session.snapshot` per read; model keeps Herdr ids verbatim; `sessionFocus` is deliberately not named "active workspace".
- Observer: single subscription, single read in flight (merged into one trailing re-read), debounce 300 ms with a 1 s minimum interval, 60 s heartbeat, reconnect backoff 1 s → 15 s, `generation` guard so callbacks of dead connections are ignored, no timers/listeners after `stop()`.
- UI: read-only "Workspaces" panel over the terminal area (available in terminal mode only; the ChatGPT view would hide it); two read-only IPC channels (`herdr:state`, `herdr:refresh`) plus the `herdr:state` push, throttled to 150 ms. Nothing reachable from ChatGPT.
- Failed approach recorded: the first HTML edit was lost by a PowerShell array-precedence mistake; a structure test now checks that every element id the renderer uses exists in the page.

## 9. Recommendation for M01-I2 / M01-I3

Because the visible workspace of ContextDeck's own client cannot be read, **do not drive ChatGPT conversation selection from Herdr focus.**

- **M01-I2 — explicit association.** Store, per Herdr workspace id, the ChatGPT conversations (URL + role) and the repository/refs, keyed by the verbatim id plus the session name; list workspaces from the observer; let the user choose the *ContextDeck workspace* explicitly (a selector in the ContextDeck UI), with a manual "adopt Herdr's last focus" action that is clearly labelled as a hint. Show orphaned associations (workspace gone) without deleting them. Migrate the per-repository preferences into the workspace record.
- **M01-I3 — conversation binding UX.** Per-workspace conversation list with roles, visible workspace↔conversation labelling in the ChatGPT tab, safeguards against sending to the wrong context. Any ContextDeck→Herdr focus change (`workspace.focus`) is global (scenario D) and mutating; keep it out unless the user asks for it and understands it moves their other clients.
- Revisit the focus question only if a future Herdr exposes a client id or a per-client focus event; `identifyActiveWorkspace` is the single place to change.
