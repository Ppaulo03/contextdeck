# M01-I3P — Chat state and lifecycle feasibility (spike)

Date: 2026-10-11 · Windows 11 · Node 24.14 · Electron 44.7.0 (Chromium 152.0.7977.130) · base: M01-I2.5.

Spike scope: can ContextDeck tell, without interfering with ChatGPT, whether a response is being generated, whether a draft exists, which conversation a view shows, and does this keep working with the view hidden. No multi-chat manager, no UI indicator, no automatic unloading, no notifications were implemented.

Legend: **Auto** = automated suite · **Harness** = script driving real Electron (throwaway profile, **logged-out** chatgpt.com, **no message was ever sent**) · **Pending** = needs the project owner at the keyboard, logged in · **Synthetic** = DOM elements injected into the throwaway page to exercise the pipeline; says nothing about the real UI.

## 1. Diagnosis (phase A)

| Topic | Today | Consequence |
|---|---|---|
| ChatGPT view | One `WebContentsView`, created once in `chat-view.js`, persistent partition, sandbox + context isolation, **no preload**, no IPC reachable from it | Any observation must come from main, passively |
| Lifecycle | Terminal/ChatGPT switch only attaches/detaches the view; 0 reloads (M01-I2.5 measurements) | The page, its JS and an in-flight response keep living while detached |
| Throttling | `backgroundThrottling` is the Electron default (`true`); never set | See §5: hidden page timers drop to 1 Hz, `requestAnimationFrame` stops |
| Navigation events | `did-start-loading/stop-loading/fail-load/navigate` only used for status text | URL changes of the SPA arrive as `did-navigate-in-page` |
| Mechanisms in Electron 44 for isolated observation | `executeJavaScriptInIsolatedWorld(worldId, scripts)`; navigation/lifecycle events; `console-message`; `debugger` (CDP); `webRequest` | Chosen: isolated-world **polling** of a boolean-only probe + navigation events. Rejected: `debugger`/`webRequest` (network visibility, forbidden), `console-message` (spoofable by the page, no world info), a preload (would expose a bridge to remote content) |

## 2. State model (phase B)

`src/main/chat/state-model.js` (pure, no Electron). Three **independent** dimensions plus identity, epoch and attention:

| Dimension | Values |
|---|---|
| `page` (PageLifecycle) | unloaded, loading, ready, error, destroyed |
| `generation` (GenerationState) | unknown, idle, responding, completed, interrupted, error |
| `draft` (DraftState) | unknown, empty, present |

Every `generation`/`draft` carries `evidence`: **observed** (a UI signal read directly), **inferred** (heuristic over signals) or **unknown**, plus a `reason`. Rules that matter:

- The stop control disappearing is **not** "completed". After `responding`: error signal → `error`; explicit interrupt notice → `interrupted`; stop gone + composer back + a finished-turn action visible → `completed` (**inferred**); stop gone + composer back, nothing else → `unknown` with reason `ended-unclassified` (the fact "it ended" is kept, the classification is not invented); composer also gone → `unknown` (could be navigation).
- Lost or malformed probe results degrade `responding` to `unknown/signal-lost`, never keep it.
- Every probe result is tagged with the **epoch** (bumped by any load or identity change) it was requested in; a result for an older epoch, a duplicate or an out-of-order sequence number is ignored. Nothing learned about conversation A can be attributed to B.
- A page load (including reload and crash) resets identity, generation and draft to unknown; nothing transient is persisted, and `responding` can never survive a restart (the observer starts from `unloaded`).
- `lifecycleAdvice(state)` (not wired to anything) returns `evictable: true` only when the page is ready, generation is idle/completed (positively known), draft is positively empty, identity is a durable conversation URL, no unviewed response is pending and the view is not visible. Everything else is a `preserve` reason.
- **Attention** (future notifications) is separate: it becomes `pending` only when a response ends while the view is hidden, and is cleared only by an explicit `viewed` (user visit); a view becoming visible is not "seen". No content is involved.

Identity (`parseConversationIdentity`) uses only the URL: `/c/<id>` conversation, `/g/<project>/c/<id>` project conversation, `/` new (no durable id yet), anything else on chatgpt.com `other`, non-HTTPS or unparsable `unknown`. A new chat that receives its durable URL by an in-page navigation **while responding** keeps its state (same conversation); in every other case a change resets everything.

## 3. Signals found (phase C)

Passive discovery on the logged-out page (control attributes only; no message text).

| Finding | Evidence |
|---|---|
| The `data-testid` values remembered from older UI versions (`prompt-textarea`, `send-button`, `stop-button`) **do not exist** on the current page; only two test ids were present | Harness |
| The composer is `textarea[name="prompt"][data-octane-input]` (`#mobile-composer-prompt` in the layout rendered), not a contenteditable `#prompt-textarea` | Harness |
| A **single** control `button[data-composer-submit]` holds both captions: `data-send-label="Enviar mensagem"` and `data-stop-label="Interromper geração"`, i.e. send and stop are the same element changing state in place; labels are **localized** | Harness |
| Idle signature (logged out, empty composer): `aria-label=Enviar mensagem`, `aria-disabled=true`, `type=submit`, `data-visually-disabled`… | Harness (captured by the diagnostic probe) |
| The attribute/label that flips **while responding**, the finished-turn action buttons, any error/“stopped” notice: **not observed** (would need a real response) | – |

Consequence: the stop signal in `state-detector.js` is a **candidate** built from three independent heuristics (stop test id; localized `aria-label` starting with stop/parar/interromper/…; a state attribute value such as `streaming`, ignoring the permanent `*-label` attributes). It is unverified until the manual run below reports the control signature while responding. The UI is not a contract: expect breakage with any ChatGPT release, and localization changes labels.

Constraints honored: the probe runs in an isolated world (sees DOM, not page JS; verified `window.__NEXT_DATA__` is invisible to it); it returns only `true/false/null` (a test feeds it a composer holding text and proves the text never leaves); the draft check reads the composer value length inside the probe and discards it; no MutationObserver (a test forbids it in `src/main/chat`), no IPC from the page, no network, cookie or debugger access (test-enforced), no new view, no preload, no listener left after `stop()`.

## 4. Prototype (phase D)

`src/main/chat/`: `state-model.js` (reducer, identity, advice), `state-detector.js` (candidate selectors, probe source, `normalizeSignals` that trusts nothing from the page), `state-observer.js` (binds one `WebContents`: `did-start-navigation` (main frame, not in-place), `did-stop-loading`, `did-fail-load`, `did-navigate`, `did-navigate-in-page`, `render-process-gone`; a timer-chained poll while ready; reports only meaningful changes), `diagnostics.js` (JSONL of transitions, ids hashed, capped 1 MB), `index.js` (activation). **Disabled by default**: set `CONTEXTDECK_CHAT_OBSERVER=1`; the only output is `<userData>\diagnostics\chat-observer.jsonl`. `window.js` only feeds visibility (`setVisible`) and the explicit visit (`markViewed`) and stops it on close. Nothing in the UI, the view lifecycle or any decision reads it.

Bugs found by running it for real and fixed (kept as tests): Electron emits `did-start-loading` for `history.pushState` navigations, which made a new chat forget its response when it received its URL (fixed by using `did-start-navigation` with `isInPlace`); the view starts loading before the observer is attached, so it never became ready (fixed and tested).

## 6. Performance (phase H, Harness, logged-out page)

| Measure | Result |
|---|---|
| Probe latency (isolated world) | 0.14 ms median visible in a bare harness; 0.7–1.2 ms with the full probe, visible or hidden |
| Idle CPU (all processes, median of 10 samples/20 s) | observer visible-idle 0.06 %, hidden-idle 0.02 %, observer stopped 0.02 % (≈ +0.04 pp when visible) |
| Memory | no extra process or measurable working set (single page, no new view) |
| Cadence | responding 1 s, visible idle 2 s, hidden idle 5 s |
| Events to main/UI | **0 IPC** to the renderer; 19 model events and 7 state changes in a 90 s session with typing, tab switches, minimize, navigation, reload |
| Detection latency (Synthetic injection) | start: 0.43 s visible, 4.07 s hidden (bounded by the 5 s idle cadence); end: ≈ 1.0 s (responding cadence) |
| Tab switch with observer on/off (real app, 20 switches) | median 9.34 vs 9.42 ms (M01-I2.5 baseline 9.2–9.4 ms), p95 12.3 vs 13.8 ms |
| Listeners added | exactly one per event on the chat contents (counted); removed exactly on `stop()`; 20 create/stop cycles leave none |

Not measured: CPU/latency during a real streamed response (needs a real response), logged-in page weight.

## 7. Feasibility matrix

| Capability | Verdict | Notes |
|---|---|---|
| Page lifecycle (loading/ready/error/crash/destroyed) | **CONFIRMADO** | Supported events, tested live including reload and redirect |
| Conversation identity from URL | **CONFIRMADO** (conversation, new, in-page, reload) / **NÃO VALIDADO** (project URL shape `/g/<project>/c/<id>`: no project available logged out) | A new chat is `new` until it gets a durable URL; identity is never guessed from titles |
| Draft present/empty | **CONFIRMADO** logged out (incl. hidden, minimize, re-attach); logged in **NÃO VALIDADO** | Presence only; depends on the composer selector |
| Response start / in progress | **NÃO VALIDADO** | Pipeline confirmed with synthetic signals; real stop-state signal not yet observed |
| Response end | **PARCIAL** | "Stopped being generated" is derivable from the same signal; *why* it ended is not |
| Completed vs interrupted vs failed | **NÃO CONFIÁVEL** | Same visible outcome (stop control gone); no known distinguishing signal. `completed` only with a corroborating turn-action signal, as an inference |
| Works with the view hidden | **PARCIAL** | Probes confirmed; real-page DOM updates while detached unverified (rAF stops, timers 1 Hz) |
| Maintainability | **NÃO CONFIÁVEL** long term | Selectors and labels are an undocumented, localized, frequently changing UI |

## 8. Decision (deliverable F)

**Can we build multiple ChatGPT conversations with state indicators and safe background preservation of responses?**

Yes for *preservation*, only partially for *indicators*:

- **Possible with high confidence:** keeping each conversation in its own loaded view (no reload, in-flight responses continue; switching ≈ 5 ms, ≈ 135 MB per view, see [m01-i2-5.md](m01-i2-5.md)); identifying the conversation of a view from the URL; knowing that a page is ready/failed/crashed; detecting that a draft *exists*.
- **Possible, best effort, must degrade to "unknown":** "a response is in progress" and "it ended" via the single send/stop control, once the manual run confirms the signal. Always show/handle `unknown`; never present it as precise.
- **Not guaranteed:** distinguishing completed / interrupted / failed; absence of false negatives (a UI change silently turns everything into `unknown`); real-time background updates.
- **Therefore the lifecycle must not depend on the detector.** The detector may only *add* reasons to preserve; no state may ever authorize destroying a view by itself.

## 9. Recommendations

- **I3A (model/association):** keep the three dimensions separate; store only durable facts (workspace ↔ conversation URL); never persist `generation`, `draft` or `attention`. Introduce the observer behind the same dev switch first, behind an interface that returns `unknown` when a signal is missing.
- **I3B (navigation):** identity = URL via `did-navigate-in-page`/`did-navigate`; treat `new` as a placeholder that upgrades when the durable URL appears; do not assume a single reused view (cost of navigating it, §I2.5: ≈ 180 ms, loses an in-flight response).
- **I3C (lifecycle):** default **preserve everything**. Candidate eligibility = `lifecycleAdvice().evictable` **and** a user-visible policy (pool limit, e.g. 3–4 views ≈ 400–550 MB) **and** explicit LRU; never evict a visible, responding, unknown, draft-present/unknown or unviewed view; an evicted conversation reloads from its URL. Do not change `backgroundThrottling` globally; if a hidden view proves to stall real responses, evaluate `false` for the chat view only, measuring CPU (timers 10× busier hidden).
- Before I3A starts: run the manual protocol below and update §3/§7 with the real signature.

## 11. Risks

False negatives (UI change → everything `unknown`, safe); false positives (`responding` from a lookalike control, e.g. a localized label on another button; an alert toast read as `error` — hence `inferred`); localization; cost of maintenance on each ChatGPT release; the OS-level occlusion that can make a hidden page behave differently on other machines; none of the above can cause data loss as long as lifecycle defaults to preserve.
