# M01-I3B-2R — Generation observability reliability

Branch `feature/m01-i3b-2r-generation-reliability`, based on the last I3B-2 commit (`8612665`). Nothing pushed or merged. I3B-2H (global activity) lives on another branch and is not part of this one.

## 1. Problem

On the real authenticated account, while ChatGPT wrote a document / writing block, the stop button stayed visible but ContextDeck concluded the response had ended (`ended-unclassified`, so "Atividade para revisar" while the answer was still being produced). The priority of this iteration is **not telling the user something false**; detecting more endings is not a goal.

## 2. Diagnosis

Audited: `state-detector.js` (probe), `state-model.js` (reducer), `state-observer.js` (cadence/timeouts), `chat-views/observation.js` (hub), `navigator.js`, the attention policy and the identity/epoch rules.

What the code did:

1. The only thing that could say "responding" was the **strong stop signal**: a stop test id, or a control with a stop label / streaming attribute **inside the composer's form** (or at known places).
2. From `responding`, **one** observation with `stop === false` and `composer === true` ended the response (`ended-unclassified`, or `completed` with turn actions). One observation, no memory.
3. From `responding`, a lost probe, a missing composer or an undeterminable signal dropped the state to `unknown` (not an ending, but the response disappeared from the UI and the next quiet observation was treated as a fresh reading).
4. Attention was raised on the transition `responding → ended` while the view was not visible.

So the system treated *"the stop control is not where I look for it"* as *"the response is over"* after a single probe.

### Root cause — status

**Not proven by direct observation.** No logged-in DOM was available in the automated environment and nothing may read the real account's page. The evidence is the code path above plus the reported symptom. The remaining hypotheses, all of which produce exactly this behaviour and all of which are now covered by the same fix:

| # | Hypothesis | Why it fits |
|---|---|---|
| H1 | During document/canvas generation the stop control is rendered **outside** the composer's `<form>` (or the form is replaced), so the probe sees `stop = false, composer = true` | one observation ended the response |
| H2 | The stop label in that mode does not match `STOP_LABEL` | same signals |
| H3 | The composer lookup falls to the structural tier and selects another editable (the document editor), so the controls read belong to the wrong form | same signals |

The fix does not depend on which one is true; the new diagnostics (§5) will identify it at the next manual homologation.

## 3. New state machine (generation, while `responding` was observed)

Principle: **the temporary absence of a signal is not proof of an ending.** Only the strong signal can *start* `responding`. Everything else can only *sustain* it, never start it.

Signals (per observation, each `true | false | null`):

| Signal | Meaning | Role |
|---|---|---|
| `stop` | stop control in its known places | strong; starts and sustains (`observed`) |
| `stopWide` | a visible control **anywhere** on the page whose label starts like a stop label (or whose test id says *stop*), excluding voice/share/record/dictation/call/camera wording, outside the controls already read | sustains (`inferred`, reason `stop-control-elsewhere`) |
| `busy` | a visible element with `aria-busy="true"` / `data-streaming` / `data-is-streaming` | weak; sustains for at most `BUSY_ONLY_LIMIT` (30) observations (`busy-signal`) |
| `composer`, `turnActions`, `error`, `interrupted`, `draft` | unchanged | as before |

Transitions out of `responding` (counters live in the model: `endProbe = { confirm, unusable, weak }`):

| Observation | Result | Counters |
|---|---|---|
| `stop = true` | `responding`, `observed`, `stop-control` | reset |
| `stopWide = true` | `responding`, `inferred`, `stop-control-elsewhere` | reset |
| `busy = true` (and `weak < 30`) | `responding`, `inferred`, `busy-signal` | `weak + 1`, others reset |
| `stop = false` and `composer = true` (nothing else active) | `responding`, `inferred`, `end-unconfirmed`, `streak = confirm` until `confirm = END_CONFIRMATIONS` (3) | `confirm + 1` |
| the 3rd consecutive such observation | `error` / `interrupted` (explicit signals), `completed` (`stop-gone+turn-actions`) or `ended-unclassified` (`unknown`) — **never `completed` without turn actions** | reset |
| anything unusable (composer missing/undeterminable, signals not determinable, probe failed/timed out, `signals-lost`) | `responding`, `inferred`, `signals-unusable`, `streak = unusable`; draft becomes unknown | `unusable + 1`, `confirm = 0` |
| `UNUSABLE_LIMIT` (20) unusable observations in a row | `unknown` (`uncertain-timeout`), **no attention** | reset |

Consequences:

- An ending needs **3 consecutive confirming observations** (≈ 3 s at the 1 s responding cadence); any sign of activity or any unusable observation restarts the count. A timeout alone never produces an ending: running out of usable evidence yields `unknown`, never `ended-unclassified`.
- Attention is raised only on a **sustained** ending of an observed response while the view is not user-visible. Not for a momentary absence, a probe timeout, an observation failure, a reload, internal navigation, an identity change, a transient visual change or a stale result (all pre-existing rules, re-pinned by tests). A valid pending attention is not cleared by a transient failure, and it is raised once.
- `ended-unclassified` is still not `completed` (rule unchanged and pinned).
- The hub exposes `uncertain` (response held on `end-unconfirmed`, `signals-unusable`, `busy-signal` or `stop-control-elsewhere`) in the summary and in the tab activity (`activity.uncertain`). The indicator still reads *responding*; `uncertain` is available to the UI/tooltip.
- Non-`responding` branches (idle, unknown, sticky ended states) are unchanged.

Existing tests were **adapted, not weakened**: the ones that asserted "one quiet observation ends the response" now assert the sustained rule (and additionally that the first N−1 observations end nothing and raise no attention); the ones that asserted "a lost signal drops `responding` to `unknown`" now assert hold-as-uncertain, no attention, and the drop to `unknown` after `UNUSABLE_LIMIT`.

## 5. Instrumentation (diagnostic mode only)

`CONTEXTDECK_CHAT_OBSERVER=1` writes `<userData>\diagnostics\chat-observer.jsonl` (`%APPDATA%\Project Dock M00\diagnostics\chat-observer.jsonl`, capped and rotated). Each transition line now carries: previous and next state, reason and evidence, `endProbe` counters, the last signals (booleans), signal availability counters in the 30 s summary, view tag, hashed conversation id, epoch, `attention`, `dtMs` (time since the previous observation), and — when the stop control is found outside the composer — `wide` (match kind and a ≤ 40-character label) and `busyCount`. No message, document or draft text is ever read; the probe still returns booleans, and the diagnostic extras are bounded control metadata (labels of buttons).

**How to send logs after a manual run:** reproduce scenario B or C, close the app, and send `chat-observer.jsonl` (and `chat-observer.jsonl.1` if present). They contain control labels such as `Parar de gerar`, never conversation content; open the file first if in doubt.

## 8. Limitations

- The root cause is not proven (§2). If the real page uses neither a stop-labelled control nor `aria-busy` during document generation, the fix degrades to the **3-observation rule plus the unusable hold**, which is weaker: a quiet page for ≥ 3 s would still be called an ending. The diagnostics are there to settle this.
- Wide matching depends on labels starting with *stop / parar / interromper / detener / arrêter / stopp*; other locales are not covered.
- Ending detection is slower by design (≈ 3 observations). A response that really ends shows its attention 2–3 s later than before.
