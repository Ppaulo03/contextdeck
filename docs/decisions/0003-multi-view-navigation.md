# 0003 — Multi-view conversation navigation: one view per loaded conversation, scoped to a workspace, never evicted

- Status: Accepted (implemented in M01-I3B-1, awaiting homologation)
- Date: 2026-10-11
- Applies to: M01-I3B-1 onwards (builds on [0001](0001-herdr-workspaces.md) and [0002](0002-chat-bindings.md))

## Context

After M01-I3A a workspace can own several conversations, but the application had one ChatGPT `WebContentsView`. The study in [m01-i2-5.md](../validation/m01-i2-5.md) measured ≈135 MB and one renderer per extra view, ≈5 ms to switch between loaded views and ≈300 ms (plus losing an in-flight response) to navigate one view. The I3P spike showed the live state of a page (generating, draft) is best effort and must never authorize destroying a view.

## Decision

1. **A `ChatViewManager` owns the views** ([manager.js](../../src/main/chat-views/manager.js), plain Node; Electron is injected as a view factory and a window host). A view is created only on demand, loads its address once, is shown by *attaching* it to the window and hidden by *detaching* it (at most one attached at any time), and is **destroyed only when the window closes** (`destroyAll`). There is no pool, no limit, no LRU, no timer, no suspension: unloading is I3C. Every view uses the one persistent ChatGPT partition and `chatWebPreferences` (one creation site, `chat-view.js`), so login, permissions, popups and clipboard behave exactly as before.
2. **Ownership and identity.** A view entry carries `scope` (the workspace key it is shown under, or none), `expectedKey` (the conversation it was opened for, or none = temporary), the identity it *actually* shows (from its URL only, via the I3A parser), an `epoch` that bumps on every identity change, and its page lifecycle. The relation between expectation and identity is *derived* (`match | loading | diverged | left | temporary | acquired`), never stored, and events never rewrite an expectation: a transient redirect heals by itself, a real divergence stays visible. A view is taken over only by an explicit action (`demote` when its conversation is opened again). **A conversation shown in a view is found by what the page shows, not by what it was opened for**, which is what prevents two views for one conversation; if two pages end up showing the same conversation the state reports `duplicates` and keeps both.
3. **A `ChatNavigator` decides which view is on screen** ([navigator.js](../../src/main/chat-views/navigator.js)): the conversations of the selected workspace only, restoring the last conversation the user *explicitly* chose there (persisted as `chat.last["<session>/<workspaceId>"] = bindingId` in `ui-state.json`; bindings stay in `chat-bindings.json`). On a workspace change a view scoped to another workspace is detached **synchronously**, before anything asynchronous (loading) can happen, and the tab is re-derived from state on every change, so a late load completion can never bring a previous workspace's chat back. No timers, no debounce: the last selection wins by construction, and stale user actions are refused because every action names the workspace it was displayed for (`context_changed`).
4. **Automatic navigation is conservative.** Restoring a conversation (startup, workspace switch) needs a `linked` binding, the chat tab showing and no workspace switch in flight; otherwise the strip shows the conversations and an empty state, and a click is required. `suspect` and `unverified` bindings open only after an explicit confirmation (two clicks); orphans belong to no visible workspace. The Auto-mode estimate can move the *visual* navigation but never creates or changes a binding, never moves Herdr's focus, and selecting a conversation never calls `workspace.focus`.
5. **Adoption of the M00 page.** The application keeps creating its initial ChatGPT page exactly as in M00 (it is the login surface and may hold the user's session state), but it is *unscoped* and never navigated. It is shown only when there is no workspace to scope to (M00 behaviour), and the first "new conversation" in a workspace hands it over *without navigating it*; later new conversations create fresh pages. Nothing is bound automatically.
6. **Temporary conversations** (a new chat, or a page that left its conversation) belong to the workspace they were opened in, appear only there (as a chip), are never destroyed, and when they acquire a durable address they are *not* bound: the I3A panel does that explicitly, after which the same view becomes the tab of the new binding. Divergence (the user navigated inside ChatGPT) re-labels what is on screen from identity and warns; the binding is untouched and the recovery is explicit (open the tab again: it gets its own view, the other keeps its page).
7. **Runtime stays separate.** Each view exposes a runtime context (`manager.runtimeOf`: lifecycle, identity, epoch; generation/draft/attention `unknown` until I3B-2) and the navigator implements the I3P `RUNTIME_PROVIDER` contract by binding id. Nothing runtime is persisted; the I3P observer stays bound to the initial page only.

## Consequences

- Positive: switching between loaded conversations costs an attach/detach (no reload, response and drafts keep living in their pages); context cannot leak between workspaces by construction; everything is unit-testable with mock views and verified in real Electron by `test/electron/multiview-harness.js`.
- Negative: memory grows ≈135 MB per loaded conversation for the whole session (no eviction yet); a startup with the chat tab showing may briefly show the unscoped M00 page before Herdr reports the workspace, then switch to the remembered conversation; background-page timers are throttled by Chromium (measured in [m01-i3b-1.md](../validation/m01-i3b-1.md)); the observer does not follow conversation views.
- Not decided here: view pool and unloading (I3C), generation/draft/attention indicators and notifications (I3B-2), automatic binding after a first message, quick keyboard navigation between conversations.
