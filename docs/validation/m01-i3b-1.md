# M01-I3B-1 — Functional multi-chat navigation

Date: 2026-10-11 · Windows 11 · Node 24.14 · Electron 44.7.0 (Chromium 152.0.7977.130) · branch `feature/m01-i3b-1-multichat-navigation`, based on the last commit of M01-I3A · Herdr 0.9.3.

Scope: several ChatGPT conversations per workspace in one window — a view manager (lazy creation, background preservation), per-workspace navigation with a remembered last conversation, a conversation strip and empty state, temporary conversations, protection against in-ChatGPT navigation. **Not** done, by instruction: view pool, automatic unloading, LRU, indicators of generating/draft/attention, notifications (I3B-2/I3C). Decision record: [0003](../decisions/0003-multi-view-navigation.md); architecture: [architecture.md](../architecture.md#multi-view-conversation-navigation-m01-i3b-1).

Legend: **Auto** = automated suite (mock views) · **Harness** = `test/electron/multiview-harness.js`, real Electron (real window, chat views, manager, navigator, IPC, overlay), throwaway profile, logged-out chatgpt.com, fake Herdr, no message ever sent · **Manual (pending)** = needs the project owner, logged in, real Herdr · **Blocked**.

The I3A homologation is still pending; this iteration builds on I3A's committed state, and the integrated I3A + I3B-1 homologation is §G.

## A. Initial diagnosis (before touching the view lifecycle)

| # | Topic | Finding | Consequence |
|---|---|---|---|
| 1 | View creation | `chat-view.js` built **one** view eagerly (`loadHome()`), `window.js` held it as `chat` and attached/detached it on tab change; `dock:reload-chat`/`chat-home` used `win.getChat()` | The factory had to become reusable, `chat` had to become "the attached view" |
| 2 | Shared session | Every view uses `chatWebPreferences(CHAT_PARTITION)`; permission handlers are set on the *session* (not on the view) | One persistent partition for all views is natural; handlers must run once (`configureChatSession`) |
| 3 | I3A contracts | `chat-bindings.json` holds bindings (+ `status`: linked/suspect/orphan/unverified/other-session); `chats:state.current` is computed from the URL of the visible view; indicator and panel read `win.getChatUrl()` | The navigator reads `bindings.all()`; `getChatUrl()` must now mean "the visible view" and be pushed on view changes |
| 4 | Identity | `parseChatUrl`: UUID key, project routes share the key; `new`/home are identity-pending | Identity of a view = what its URL shows; titles are never used |
| 5 | Runtime contract | `chat/runtime-contract.js` + I3P observer bound to one `WebContents` | Per-view runtime context only (lifecycle, identity, epoch); the observer stays on the initial page |
| 6 | Resize / tabs / focus / overlays | `resizeChat` positions one view under a 52 px bar and above the footer; Ctrl+Tab handler is installed on each web contents; the overlay is a view re-added on top when opened | Bounds get a second offset (conversation strip); every view gets the shortcut handler; attaching a view must raise an open overlay |
| 7 | Regression risks (authenticated ChatGPT) | partition/identifier drift; recreating the initial page; reloading on switch; a hidden page behaving differently; focus after an empty state; popups/permissions per view; strip height vs bounds | All addressed below; the ones needing a logged-in account are in §G |

## B. Technical proposal (short)

1. `ChatViewManager` (plain Node, injected `createView`/`host`) owns views: create on demand, load once, attach/detach (≤ 1 attached), destroy only in `destroyAll()`.
2. `ChatNavigator` derives the visible view from (selection, bindings, last-choice preference, mode) in an idempotent, synchronous `reconcile()`; user actions carry the workspace they were rendered for.
3. Adoption of the existing view: keep creating it as in M00, **unscoped and never navigated**; first "new conversation" hands it over without navigation.
4. Persist only `chat.last["<session>/<workspaceId>"] = bindingId` (explicit choices) in `ui-state.json`.
5. Verify in real Electron that detaching preserves the page before relying on it (§E.2).

## C. Architecture implemented

Summarised in the architecture document. Components and contracts:

| File | Role |
|---|---|
| `src/main/chat-views/manager.js` | Registry, attach/detach, identity/epoch/relation (`match, loading, diverged, left, temporary, acquired`), `findByKey`, `findNeverReached`, `duplicates`, `runtimeOf`, `destroyAll` |
| `src/main/chat-views/navigator.js` | `reconcile`, `selectBinding`, `newConversation`, `selectTemporary`, `openUnscoped`, `setMode`, `getState`, runtime provider (`getRuntime(bindingId)`, `subscribe`) |
| `src/main/chat-view.js` | One factory for every ChatGPT page (events → manager); permissions set once per session |
| `src/main/window.js`, `window-metrics.js`, `overlay.js` | Host (attach/detach/bounds/raise), 52 + 34 px offset, `getNavigator`, `getChatUrl` = visible view |
| `src/main/ipc/chatnav.js`, preload | `chatnav:state/select/select-temporary/new/open-unscoped` (UI window only) + `chatnav:state` push |
| `src/main/persistence/ui-state.js` | `chat.last` (ids only, validated, ≤ 100, older files load) |
| `src/shared/chat-nav-view.js`, `src/renderer/components/chat-strip.js`, `index.html`, styles | Strip (`role=tablist`, roving tabindex), `+`, **Gerenciar**, empty state, spinner in tab, tokens `--chatbar-h` |

**Ownership.** A view is owned by the conversation it was opened for (`expectedKey`) and shown under one workspace (`scope`); what a tab shows is decided by what the page *shows* (identity). **Lifecycle.** Created lazily; loaded once; hidden = detached; closed only when the window closes. **Lazy loading.** Nothing but the application's initial page loads at startup; restoring the last conversation creates exactly one view, only when the chat tab is showing and no workspace switch is pending. **Workspace navigation.** A → B detaches A's view synchronously, shows B's remembered conversation or an empty state; B → A restores A's. **Last conversation.** Only an explicit tab click is remembered (never an in-ChatGPT navigation, never an Auto-mode estimate); a temporary conversation does not replace it. **Temporary conversations.** Opened under a workspace, listed only there, never destroyed, never bound automatically; a page that acquires an address stays unbound until the I3A panel binds it, then it *is* that tab's view.

## D. Navigation flows

- **Open a conversation** (`selectBinding`): refuse unless chat tab, no pending switch, same workspace as displayed, binding in that workspace; `suspect`/`unverified` need `confirm`; orphans/other sessions never open → reuse the view that shows it, else the one still on its way / that never settled on it (redirect), else demote any view that *did* leave it and create one → show → remember.
- **Workspace change**: selection event → reconcile → visible view scoped elsewhere is detached → explicit pick of this workspace → remembered conversation if `linked` (view created only if allowed) → else empty state (`no-conversations` / `select-conversation` / `not-verified` / `no-workspace`).
- **Terminal ⇄ chat**: `setMode` reconciles first, then attaches/detaches; the terminal tab never creates a view.
- **Navigation inside ChatGPT**: events update identity and epoch; the tab of what is really shown lights up; a conversation that is bound elsewhere or unbound appears as a warning chip; bindings and the remembered choice are untouched; re-opening the old tab gives it its own view (the page that left is kept as a temporary one).
- **Bindings change** (I3A panel): `notifyChats` also reconciles: an unbound conversation's view becomes temporary (still on screen), a reassigned one follows its binding while it still shows it, a temporary page that shows a conversation just bound in its scope becomes its tab.

Bugs found by the harness and fixed (kept as tests): (1) with a logged-out profile (and for an unavailable conversation) ChatGPT commits `/c/<id>`, finishes loading, then its SPA redirects to `/` ≈ 0.1–0.4 s later; selecting that tab again spawned a new view on every click. Fix: a view that leaves its conversation within 3 s of finishing loading on it never "reached" it and stays that tab's view; one that left later (the user pressed "new chat") is kept as a temporary page and the tab gets a fresh view. ## F. Risks and limitations

1. **Memory grows ≈ 135 MB per loaded conversation for the whole session** (no eviction by design); five loaded conversations ≈ 1.4–1.5 GB with the UI.
2. **Startup with the chat tab showing** may briefly show the unscoped M00 page until Herdr reports the workspace; then the remembered conversation is created and shown (the unscoped page stays alive, unused, until a "new conversation" adopts it).
3. **Auto-mode flapping** (Herdr focus moving between workspaces while the chat tab shows) creates the remembered conversation's view the first time each workspace is seen (selection settled, linked binding). It never binds or focuses.
4. **Background throttling**: hidden pages run timers at 1/s and no `requestAnimationFrame` (Chromium); message-channel work and networking are not throttled. Whether a *real* response keeps streaming while hidden is unvalidated until scenario C. `backgroundThrottling` is unchanged.
5. **The 3 s redirect window** is a heuristic: a user who leaves a conversation within 3 s of its load finishing has that view treated as never having shown it (a later tab click reuses it instead of creating a fresh one).
6. The I3P observer follows only the initial page; indicators for conversation views are I3B-2.
7. Drafts and responses live only in the pages: closing the application loses them (not promised otherwise).
8. A conversation that cannot load (deleted, no access) keeps its single view showing whatever ChatGPT redirected to; it is never retried automatically (only by selecting it when its load *failed*).

## G. Manual homologation (Windows, integrated I3A + I3B-1)

Preparation: back up `%APPDATA%\Project Dock M00\ui-state.json` and `chat-bindings.json`; real Herdr with two disposable-or-real workspaces A and B (do not use the `default` session for experiments that mutate); `npm start`; logged-in ChatGPT; four real conversations C1–C4 (ids in their addresses). Never delete conversations. Do not automate prompts.

**A — First workspace**
1. Select workspace A. ChatGPT tab: the strip shows "ChatGPT · A" and, with nothing bound yet, the empty state *Este workspace ainda não tem conversas*.
2. **Nova conversa** → a ChatGPT page opens; open C1 through ChatGPT's own sidebar, then **Gerenciar** → bind current as "C1" (I3A flow). Repeat for C2 (use **+** again): both are tabs now.
3. Click between C1 and C2 ten times: the page never reloads (no spinner after the first load, scroll position and any text in the composer stay).

**B — Second workspace**
1. Select workspace B: A's tabs and page disappear; empty state. Bind C3 (via **Nova conversa**/**Gerenciar**).
2. Select A again: C2 (the last one you clicked) is back, same page, no reload.
3. In B, bind C4; switch B ⇄ A repeatedly: each shows only its own conversations, never the other's.

**C — Response in progress** (your own prompt)
1. In C1 start a long answer. Switch to C2, then to workspace B, work there, then return to A and C1: the answer kept streaming (note if it stalled while hidden, and how long it took to catch up).

**D — Drafts**
1. Type text in C1's composer without sending. Switch C2, workspace B, Terminal tab, back: the draft is intact.

**E — Navigation inside ChatGPT**
1. In C1's page click C2 in ChatGPT's sidebar: the C2 tab lights up (C1's does not); no vínculo changed (open **Gerenciar**).
2. Click the C1 tab: it gets its own page (C2's stays). Click a conversation that is bound to B from ChatGPT's sidebar while in A: a warning chip names it with B's workspace id, no tab of A lights up.
3. Press "New chat" inside a conversation's page: the tab shows the warning; click the tab again → a new page for it; the other page remains as *Nova conversa*.

**F — Persistence**
1. Select C1 in A and C4 in B; quit and restart: the strip restores them (only the last one of the current workspace is loaded; others load when you click them). Herdr did **not** change workspace by itself. ChatGPT is still logged in.
2. Restart with the Terminal tab active, select a workspace, open ChatGPT: the remembered conversation loads on entering the tab.

**G — Regressions**
Terminal tab, `Ctrl+Tab` from every view and from the empty state, workspace dropdown (and its menu over the ChatGPT view), Auto/Manual, the I3A panel and indicator, clipboard in ChatGPT, upload in a non-first conversation, Git diff/show/ZIP, window resize (the chat view always sits under the strip and above the footer), Alt+Tab (focus returns to the visible view), login popups.

**H — Safety**
1. Select workspace A, then in Herdr move the focus to B (Auto mode): the ChatGPT tab switches to B's conversations without ever showing A's under B; no binding changed.
2. With the I3A panel open on A, change the workspace: its banner appears and bind buttons are blocked (I3A rule).
3. Disconnect Herdr (disposable session): tabs show as unverified; clicking one needs a second click (confirmation); nothing opens automatically after restart.

Report each item as confirmed / partial / failed, with the date.

## H. Pending for I3B-2 and I3C

- **I3B-2:** wire the observer/runtime to each view (generation, draft, attention indicators; `ended-unclassified` stays unclassified), notifications, quick keyboard navigation between conversations, refined recovery for in-ChatGPT navigation (offer "bind this page here"), a tab for a conversation that failed to load, optional "bind this page" action directly in the chip.
- **I3C:** view pool, LRU, unloading — only behind `lifecycleAdvice` plus a user-visible policy, never for a responding, draft-present, unknown or unviewed view; the manager already isolates ownership and destruction (`destroyAll` is the single destroy site), so an eviction policy is an addition, not a rewrite.
